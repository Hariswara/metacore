What Module 3 actually does, file by file

The dashboard form is not the M2 signal. The gate is not System 2. System 2 is not the meta-RL. Reward in the live pipeline belongs after M4, not inside a mock verifier. This page is the correction pass over those mix-ups, against the committed code.

Picture one fake storm. Everything else is counting those.

plain version — no RL words yet

We do not have a live cyclone. So the code invents practice storms and drills the gate on them. One invented storm is called an episode. That is the whole word. A story from “grid is fine” → “elevated” → “severe” → “extreme,” then it ends.

During that one storm the gate is asked, over and over: cheap reaction (System 1) or expensive plan (System 2)? Each time it is asked, that is one step. “Gating step” just means “one of those questions.” Default: 80 questions per storm = episode length 80.

System 2 is the expensive one — slower, spends the thinking budget. You are only allowed to pick it 45 times in that one storm (budget). After that the code refuses S2 and you are stuck with S1 until the storm ends. That is “expensive thinking.”

Clicking Run does not type a u. It starts a drill: invent 150 practice storms, grade the gate, then invent 12 more storms without changing the gate (that is “frozen” — exam, not practice) and plot those scores. The u values you later see in the log were generated inside those invented storms, from Duwaragie’s file, one per step.

What you type on the website

how the drill is set up — you pick this

How many storms to practice on, how long each storm is, how many expensive plans are allowed, and how harshly we punish “thinking when we shouldn’t.” None of this is a voltage or a node.

What the gate sees at one question

one step inside one storm — M2 + fake M1

Right now, this second: how unsure is M2 (u), is it a cyclone or a blackout, how bad is the hazard, which nodes are at risk. Then it answers S1 or S2. That answer is what you want to watch, not the form.

What is learned — one sentence

architecture, not a guess

Only the gate is trained. policy.py is a 2-action REINFORCE net: pick System 1 or System 2. That is the “toy meta-policy.” System 1 is rule-based. System 2 is a hand-written stand-in for a real (non-ML) survival optimizer. The project’s own design rule: ML only where no adequate rule exists — forecast vulnerability (M1), isolate epistemic uncertainty (M2), learn when to deliberate (the gate). Not learn the control actions. Source: docs/architecture/overview.md, module3.proto comment on ProcessPath.

The words on the form, in English

You are not typing grid data. You are setting up a practice session for the gate (“when should I spend System 2?”). Defaults in brackets.

Form saysIn EnglishDefault
Seed A lucky number for the random fake storms. Seed 0 always invents the same 150 storms. Seed 7 invents a different set. That is all “replayable” means: run it twice, get the same drill, so you can debug. It is not a measurement from the microgrid. 0
Episode One fake storm, start to finish. Calm at the beginning, extreme at the end, then stop. Not a real event. Not “eval.” Just one practice (or test) story. —
Episode length How many times during that one storm the gate is asked “S1 or S2?” 80 means: 80 questions, then the storm is over. Each question is one row of fake M1 (how bad is it, which nodes) plus one row of M2 (u, cyclone vs blackout). Those 80 questions are the “gating steps.” Nothing mystical. 80
Budget / episode How many of those 80 questions are allowed to be answered with System 2. 45 means: you may think hard 45 times this storm. The 46th time the code ignores the gate and forces System 1. Like 45 expensive phone calls on a prepaid card. 45
Train episodes How many fake storms we practice on. 150 storms × 80 questions = 12,000 “S1 or S2?” answers used to nudge the net. This is “how long to train” — train the gate, not System 1, not System 2. 150
Eval episodes After practice, we stop changing the net (“frozen policy” = the student puts the pencil down) and run 12 more storms just to score it. Those 12 are what the charts average. If we kept training during this part, we would be grading homework we let it copy. 12
Deliberation cost A points fine every time the gate picks System 2. Default 0.10 off the score. That is the “toll” for expensive thinking. It is a number we invented so the gate does not pick S2 on every question. It is not a real millisecond. The 2 ms / 18 ms in the log are also made up, for the contract. 0.10
Benefit scale How many points you gain when you correctly pick S2 on a cyclone-like step. Must be bigger than the toll, or the gate never pays to think. 4.0
Sensing penalty Extra fine if the gate picks S2 during a blackout (missing data). −1.2 means “you just wasted an expensive plan on a grid you cannot see.” −1.2

Are these auto-generated? No. You (or the defaults) set them. What is auto-generated when you click Run: the fake storms themselves (synthetic_context.py) and the per-step u / trigger_reason draws from Duwaragie’s file (m2_stream.py).

What the fuck is m2_stream.py

it is a file, not a live socket

M2 (Duwaragie) published a JSONL mock: one JSON object per line, schema m2-out/0.3. A copy lives at sample_m2_to_m3.jsonl next to the M3 code. m2_stream.py does two jobs: load that file, then replay it — bootstrap-resample with tiny jitter — so an 80-step episode can be longer than the file. It does not import M2’s Python. It does not call M2 over the network. When M2 is live, this file gets replaced by the real stream; the field names stay the same.

What one M2 record actually contains (from the committed file):

{
  "epistemic_uncertainty": 1.0,          // u  — how untrustworthy, 0..1
  "trigger_reason": "value",             // none | value | sensing | both
  "competence_drop": true,               // did either axis fire
  "observed_fraction": 0.42857,          // share of M1 features that were QUALITY_OBSERVED
  "state_class": 0,                      // argmax safety class
  "class_probabilities": [0.33, 0.33, 0.33],
  "aleatoric_proxy": 0.0,                // loaded, not used by the gate
  "schema_version": "m2-out/0.3"
}
trigger_reasonPlain meaningWhat the gate is taught to do
noneordinary state, data is therestay S1 unless severity is extreme
valuecyclone-like: state unlike training. u ≈ 1escalate to S2 when it is actually bad
sensingcomms blackout: we cannot see. observed_fraction under the floorstay S1 — thinking on absent data buys nothing

Replay also pairs the reason with M1 severity: severe/extreme steps are more likely to draw a value row, calm steps a none row. Still only published M2 numbers, jittered.

synthetic_context.py — the fake M1

Zayan’s live SystemContext is not wired yet. This file invents an episode that looks like module1.proto’s SystemContext so the gate can train. One episode is four quarters: normal → elevated → severe → extreme.

priority.py — the critical-node map from the meeting

A frozen lookup, not learned. Both controllers import it. Tier 1 is never shed.

policy.py is the gate — how it chooses S1 vs S2

There is no if/else at decision time. There is a tiny neural net that emits two scores, then a coin-flip (training) or a greedy pick (eval). It was started from an if/else by behaviour cloning, then REINFORCE nudged the weights.

What each function in that file is

NameWhat it does, in English
nn.Linear(a, b) A learned matrix multiply: y = xWᵀ + b. Maps an a-vector to a b-vector. The entries of W and b are the things REINFORCE updates. First layer: 12×32 weights. Last layer: 32×2 weights — two scores, one per action.
nn.Tanh() tanh(x) = (eˣ − e⁻ˣ) / (eˣ + e⁻ˣ). Squashes every number into (−1, 1). Classic MLP activation (LeCun et al., Efficient BackProp). Not ReLU here — tanh keeps signed features (u, reason flags, budget) from collapsing to “on/off.”
forward(x) Run the three Linear layers. Returns raw logits, not probabilities.
Categorical(logits) Softmax the two logits into P(S1), P(S2), then treat that as a coin. Training calls sample() so the net explores. Eval in run_demo / evaluate uses argmax — always the more likely action, no coin.
act(obs) forward → sample → return (action as 0 or 1, log π(a|s)). The log-prob is what REINFORCE multiplies by return.
action_probs(obs) Softmax only. For inspection, not used on the hot path.
reinforce_update(...) After a batch of episodes: for each step, take the remaining sum of rewards Gₜ, standardise those returns inside the episode, then loss = −log π(a|s) · Ĝ. Gradient ascent on expected return (Williams 1992). Gradients clipped at 1.0. Adam steps the weights (Kingma & Ba 2015).
REINFORCE in this file, undiscounted:
Gₜ = rₜ + rₜ₊₁ + … + r_T    then    Ĝ = (G − mean G) / std G
θ ← θ + α · Ĝ · ∇θ log πθ(aₜ | sₜ)

Honest code note: a moving-average baseline is computed and returned, but the loss uses (R − 0.0) after standardising. The “baseline” you see printed during training is a running mean of returns, not the advantage subtractor. Standardising inside the episode is doing the variance-reduction job instead.

The if/else it was cloned from — not the live rule

40 warm-start episodes copy this heuristic into the net (behaviour cloning / Pomerleau 1991). After that, REINFORCE is free to drift. Eval still usually tracks it closely.

If the 12 numbers look like…heuristic_action returns
sensing flag on, value flag off (blackout only)0 = S1
value flag on, severity ≥ severe (index ≥ 0.66)1 = S2
value flag on, severity ≥ elevated, u ≥ 0.851 = S2
no value flag, severity extreme, u ≥ 0.51 = S2
anything else0 = S1

Plus a hard override the net cannot beat: if budget_remaining ≤ 0, GatingEnv.step forces S1 and sets budget_exhausted_fallback=true. That is not an agent action. It is the budget wall.

System 1 — what happens inside, and a real output

system1.py · origin = SYSTEM1 · rule-based, not trained

Reads only max_node_vulnerability, top_at_risk_nodes, and whether trigger_reason is sensing/both. Never reads u. Sheds lowest-priority nodes first. Never touches breakers or dispatch. Under sensing, shed_scale = 0.45 instead of 0.8 — cut less, because it cannot see the grid.

breakersnone
load_shedNode N8 — shed 11.2% (tier 3)
dispatchnone
rationaleS1 reactive shed vuln=0.14

Sensing-fallback example in the same file: rationale S1 sensing-fallback shed vuln=0.21, still no breakers, still no dispatch. That is the entire S1 vocabulary.

System 2 — what happens inside, and a real output

naming collision, corrected

System 2 is not the toy meta-RL. The toy meta-RL is the gate. system2.py is a hand-written stand-in for a deliberative survival optimizer: protect tier-1, shed less total, bump diesel/BESS dispatch, keep a critical breaker closed. Zero learning. The intended replacement is a real optimizer that proposes the same three lists — not a second neural net, and not an OpenDSS caller (only M4 may open the digital twin).

SYSTEM 2 — from sample_m3_to_m4.jsonl vuln = 0.63 · u = 1.0 · reason = value
breakersEdge E_crit_1 — CLOSE
load_shedNode N11 — shed 25.0% (tier 3)
Node N8 — shed 9.8% (tier 3)
dispatchNode N4 — 147.4 kW, 10.0 kVAR
rationaleS2 survival opt vuln=0.63 protect-tier1

Dispatch formula in the stand-in: p_kw = 50 + 150 × vuln + Uniform(-5, 5). That jitter is why two S2 plans with similar vuln are not identical. Reads only vulnerability and the at-risk node list. Never reads u or trigger_reason.

Why there is a Gym environment

Gymnasium (Towers et al. 2024; successor of OpenAI Gym) is the standard wrapper for “agent takes an action, world returns next observation + reward.” GatingEnv is that wrapper for the 2-action MDP. It is not a power-system simulator.

Gym pieceIn this module
observation_spaceBox of length 12 (the vector above)
action_spaceDiscrete(2) — 0 = S1, 1 = S2
reset()New 80-step M1 scenario + resampled M2 stream, budget refilled
step(action)Run S1 or S2, score a reward, advance one step, maybe truncate at episode_len
info dictEverything the dashboard later shows: proposed plan, u, reason, benefit, cost, mock verdict

Sutton & Barto ch. 3 is the MDP language (state, action, reward, episode). Gym is just the Python API for that loop. Without it you would write the same for-loop by hand; REINFORCE does not require Gym, the starter used it so the env is a single object.

Where the reporting / reward sits — after M4, not before

argument, not a guess

The live pipeline is: M3 proposes → M4 judges → that verdict feeds back into M3’s cost model. The contract register in docs/roadmap.md already says so: “Approve/reject decision + reason | owner M4 | consumer M3.” M3_TO_M4_CONTRACT.md says a REJECT should “eventually feed back as deliberation-cost pressure, not just a discarded action.”

So the reporting signal for REINFORCE belongs after the judgment. If you score the gate before M4, you are training “did we pick the heuristic we already wrote,” not “did the action survive physics.” That is the wrong objective.

Therefore verifier.py / mock_verify is a training-time stand-in for Hariswara, not a fifth pipeline stage and not something to show as “the verify step.” Deleting the file today, with M4 not live, would just silently drop reject_penalty from the reward — the gate would stop being punished for S1-under-extreme and for shedding tier-1. Keep the file until real M4 verdicts replace it. Do not display it as Module 3’s job.

What the step reward is, today, inside gating_env.py:

r = benefit − deliberation_cost − reject_penalty

benefit is cause-aware:
· S2 on sensing-only → sensing_escalation_penalty (−1.2)
· S2 on a calm, sure, non-value step → needless_escalation_penalty
· S2 on value/both → benefit_scale × severity × u  (the “correct escalate” payoff)
· S1 on value/both when severity is already severe → −missed_escalation_penalty
· otherwise 0

reject_penalty (1.5) fires only when mock_verify says REJECT. In the live system that term is M4’s verdict, arriving after the action was proposed.

Who does the evaluation

Not M4. Not the dashboard. evaluate.py, called at the end of run_demo.py, after training freezes.

  1. always-S1 baseline — every step action=0. A dumb “never think” policy.
  2. always-S2 baseline — every step action=1, until the budget wall forces S1. A dumb “always think” policy.
  3. trained policy — greedy argmax of the net. Must beat both on total reward, and spend ≤ always-S2 on average deliberation cost.
  4. escalation by severity — fraction of steps that ran S2, sensing-only dropped so blackouts don’t break the curve. Thesis check: normal ≤ elevated ≤ severe ≤ extreme.
  5. escalation by trigger_reason — sensing should sit at 0; value/both should be high.

The dashboard charts are exactly those five numbers, averaged over “Eval episodes.” The decision log under them is one extra frozen episode, emitted as ProposedControlAction + GatingDecision pairs. Hariswara’s real verifier only ever sees the action; the M2 fields and the mock verdict in the expander are dashboard-only context.
